## 1. 软删除 vs 物理删除怎么选？为什么同一张表上两种唯一约束并存？

**答案要点**

- 软删除（`deleted_at` 置时间戳）：数据可恢复、可追溯、不破坏外键引用；代价是所有查询要带 `deleted_at IS NULL` 过滤，唯一约束变复杂。
- 物理删除：干净、省空间，但被外键引用时删不掉，且不可恢复。
- 本项目 `account` 上两种唯一策略对比是经典考点：
  - `username` **全局唯一索引**：登录名是身份标识，永远不可复用（防止"冒名顶替"：旧用户删了，新人注册同名账号会造成数据归属混乱）。
  - `email`/`phone` **部分唯一索引**（`WHERE deleted_at IS NULL`）：只约束"活着"的数据，软删后邮箱可复用（用户注销后换绑场景）。
- 部分唯一索引（partial unique index）= 带 WHERE 条件的唯一索引，只索引满足条件的行，更小更快。

**项目代码**：[org.py](file:///Users/xuhonghui/Project/oi_trainer/app/models/org.py) 中 `Account.__table_args__`；演示见 [阶段1_基础_crud.py](file:///Users/xuhonghui/Project/oi_trainer/scripts/阶段1_基础_crud.py) 1.1 节（软删后同 email 重建成功、同 username 重建被拒）。

## 2. "先查再插"和"直接插 + 唯一约束兜底"哪个对？

**答案要点**

- 先查再插有**竞态窗口**（TOCTOU）：两个并发请求同时查到"不存在"，然后都插入 → 重复数据。
- 正确做法：**唯一约束（数据库层）才是最终防线**，插入时捕获 `IntegrityError` 转业务提示。
- 那"先查"还有用吗？有——用于**提前给出友好报错**（如注册页即时提示"用户名已存在"），但它只是体验优化，不能保证正确性。
- 本项目两者都用：service 先 `exists_by_username` 预检，repo flush 时捕获 `IntegrityError` 兜底。

**项目代码**：[services/account.py](file:///Users/xuhonghui/Project/oi_trainer/app/services/account.py) `create_account`；预检在 [repositories/account.py](file:///Users/xuhonghui/Project/oi_trainer/app/repositories/account.py) `exists_by_username`。

## 3. offset 分页的原理？有什么问题？

**答案要点**

- `LIMIT n OFFSET m`：数据库先扫描/排序出前 m+n 行，丢弃前 m 行。实现简单、支持跳页。
- 问题：**深分页劣化**——OFFSET 越大，扫描丢弃的行越多（第 10000 页 = 白扫几十万行）；且数据变动时翻页会重复/漏数据。
- 替代方案 **keyset 分页（游标）**：`WHERE (created_at, id) < (上一页末行值) ORDER BY created_at DESC, id DESC LIMIT n`，恒定复杂度，但不支持跳页。本项目题目列表（任务 1.7）用 keyset，届时对比。
- 辅助手段：排序字段必须加**唯一字段（如 id）做稳定 tiebreaker**，否则同值行翻页顺序不稳定。

**项目代码**：[repositories/account.py](file:///Users/xuhonghui/Project/oi_trainer/app/repositories/account.py) `list_page`；排序解析 [schemas/common.py](file:///Users/xuhonghui/Project/oi_trainer/app/schemas/common.py) `apply_sort`。

## 4. 批量插入/批量删除怎么做？注意什么？

**答案要点**

- 批量插入：ORM 层 `session.add_all()`（逐对象 INSERT，拿回主键）vs Core `insert().values([...])`（一条多值 INSERT，更快但默认不逐行回对象）。批量大会话用 Core。
- 批量更新/删除：一条 `UPDATE ... WHERE id = ANY(:ids)` 搞定，**不要在 Python 里循环逐条 UPDATE**（N 次网络往返）。
- 事务语义：批量操作要么全成功要么全回滚——任一冲突时捕获异常回滚，避免"插了一半"。
- 返回 rowcount 能让调用方知道"实际删了几条"（已删的不重复计数）。

**项目代码**：[repositories/course.py](file:///Users/xuhonghui/Project/oi_trainer/app/repositories/course.py) `create_batch` / `soft_delete_batch`。

## 5. 状态机流转为什么要在应用层校验，只靠数据库 CHECK 不够吗？

**答案要点**

- CHECK 约束能校验"值域"（如 `capacity > 0`），但**不擅长校验"流转路径"**（draft→published 合法、archived→draft 非法）。
- 流转合法性是**业务规则**，写在应用层（service）里：可读、可测试、报错信息友好；CHECK 只做值域兜底。
- 面试延伸：并发下状态流转要防"重复生效"——用条件 UPDATE（`UPDATE ... WHERE status='pending'`，影响行数=0 说明已被别人改过），阶段 3 订单支付会练。

**项目代码**：[services/course.py](file:///Users/xuhonghui/Project/oi_trainer/app/services/course.py) `ALLOWED_TRANSITIONS` + `update_course`。

## 6. 树形结构（如知识点树）在关系型数据库怎么建模？

**答案要点**

- 最常用 **邻接表（adjacency list）**：每行存 `parent_id` 自引用外键。增删改简单、省空间；代价是查整棵子树要递归。
- 同层排序加一个 `order_index` 列。
- **防环**（把节点挂到自己的子孙下会破坏树）：应用层沿祖先链检查，本项目用循环查（树小够用）；进阶方案有递归 CTE 一次查完祖先、`ltree` 扩展、触发器。
- 查子树/路径用**递归 CTE**（`WITH RECURSIVE`）——阶段 2 任务 2.5 专门练。
- 其他模型对比（面试加分）：路径枚举（path 字符串）、闭包表（closure table）、嵌套集（nested set）——各有读写权衡。

**项目代码**：[services/knowledge_point.py](file:///Users/xuhonghui/Project/oi_trainer/app/services/knowledge_point.py) `_assert_not_cycle`；[repositories/knowledge_point.py](file:///Users/xuhonghui/Project/oi_trainer/app/repositories/knowledge_point.py) `list_children`。

## 7. `updated_at` 这类审计字段怎么自动维护？异步 ORM 有什么坑？

**答案要点**

- 三层手段：`server_default=func.now()`（建行时数据库给默认值）、`onupdate=func.now()`（ORM/Core UPDATE 时 SQLAlchemy 自动拼进 SET）、数据库触发器（最重，本项目不用）。
- 坑 1：PG 只对 INSERT 默认走 RETURNING 取回 server 默认值；**UPDATE 后 onupdate 列会被标记为"过期"**，下次访问属性会触发一次隐式"重新加载"。
- 坑 2：异步会话里隐式重新加载 = 同步 IO → `MissingGreenlet` 报错。解决：UPDATE 后显式 `await session.refresh(obj)` 把最新值取回来。
- `expire_on_commit=False`：commit 后不清空对象属性，避免 commit 后访问属性又触发一次查询（异步下同样会炸）。

**项目代码**：[repositories/account.py](file:///Users/xuhonghui/Project/oi_trainer/app/repositories/account.py) `update` 中的 refresh 注释；[db.py](file:///Users/xuhonghui/Project/oi_trainer/app/core/db.py) `expire_on_commit=False`。

## 8. 乐观锁是什么？为什么 `class_group` 要加 `version` 列？

**答案要点**

- 场景：班级报名要校验"名额未满再 +1"。并发下两个请求同时读到 `enrolled_count=29`（容量 30），都判断可报 → **超卖**。
- 悲观锁：`SELECT ... FOR UPDATE` 把行锁住，别人排队。简单可靠，但锁竞争大时吞吐量下降。
- 乐观锁：加 `version` 列，更新时 `UPDATE ... SET enrolled_count=enrolled_count+1, version=version+1 WHERE id=? AND version=读到的值 AND enrolled_count < capacity`——影响行数=0 说明被别人改过，重试。无锁、高并发友好，但冲突多时空转。
- 面试加分点：乐观锁的 `version` 也叫"基于版本号的 CAS"；数据库 CHECK（`enrolled_count <= capacity`）是最后兜底，即使应用 bug 也不会超卖到库里。

**项目代码**：[org.py](file:///Users/xuhonghui/Project/oi_trainer/app/models/org.py) `ClassGroup.version` 与 CHECK 约束；并发报名实战在阶段 3（任务 3.1/3.2），本轮只在 CRUD 里把 `version`/`enrolled_count` 排除在通用更新之外。

## 附：本阶段踩过的两个工程坑（面试可以当"项目经验"讲）

1. **响应模型泄漏**：SQLModel 泛型分页 `Page[XxxRead]` 构造时不校验 `items`，ORM 对象原样返回会把 `hashed_password` 这类敏感字段泄到接口里。教训：**响应模型必须在边界显式 `model_validate`**，或返回前确认字段白名单生效。
2. **标量查询的返回值形态**：`sqlalchemy.select` + `session.exec` 返回的是 Row 元组（`(False,)` 也是 truthy），`sqlmodel.select` 包装后才直接给标量。混用会导致 `exists()` 永远为 True 这种隐蔽 bug。
